# Warband MCP — actual game integration

Architecture:

```text
MCP client → stdio MCP server → authenticated local HTTP bridge
                                   ↕
                 vanilla Warband game scripts (HTTP operation 380)
```

**CUA is not a backend or dependency.** It is only the developer's separate
launch/visual-validation tool. There is no screen scraping in this MCP server.
The Python bridge/MCP server use portable networking and filesystem APIs;
the mod uses vanilla Warband bytecode, not Hyprland, X11, WSE or memory injection.
Only Linux/Proton is being tested here; Windows/macOS compatibility is not yet
live-verified. Game and bridge must run on the same host for this loopback build.

## Current tools

- `warband_get_state`: engine-sourced gold, troop ID, position, mission HP,
  clock, acknowledgement and telemetry age.
- `warband_display_message`: queue a game `display_message` operation.
- `warband_command_status`: queued / dispatched / acknowledged / rejected /
  expired / interrupted.
- `warband_refresh_scene_agents` and `warband_scene_agents`: complete, bounded
  census of up to 64 living human agents, with engine IDs, teams, HP and positions.
- `warband_relocate_player`: ground-aligned **debug teleport**, limited to 10m.
  This is not walking, battle AI, or campaign travel.
- `warband_npc_say`: supplied text rendered in the targeted NPC's real dialogue UI.
- `warband_dialogue_event`: game-reported opening/closing of that conversation.
- `warband_capabilities`: implemented/unimplemented capabilities and restrictions.
- `warband_refresh_campaign` and `warband_campaign_result`: bounded pages of
  party members/prisoners, player inventory, character attributes/skills, active
  world parties and active quest slots. Pages survive bridge restart. Wait for
  `complete=true`; `next_offset` requests the next page. A multi-page collection
  is **not** one atomic snapshot: game time may advance between pages.

World exports currently include hidden parties and therefore represent an
omniscient debug view, not legitimate player scouting. Definition labels do not
track player-renamed parties/items; quest titles remain unexpanded templates,
not rendered journal text. Each page has at most 16 rows. Campaign requests
require fresh campaign telemetry and are rejected when a mission is entered.
Campaign export evidence and remaining validation gaps are documented below.

NPC text is generated by the calling agent, not a provider hard-coded into this
server. The current conversation is one turn with a visible "Back to training"
choice; arbitrary player free-text replies and persistent NPC memory are not
implemented. Census names come from module definitions, not live renamed names.
Campaign action tools remain unimplemented.
Acknowledgement means the game executed the operation, not screenshot proof.
CUA supplies independent visual proof during development.

Revision 3 installs polling in 41 single-player mission templates, excludes
multiplayer templates and guards game operations against multiplayer execution.
Training-yard and village integration are live-verified; every other mission
has not individually been exercised. Telemetry includes mission template, flags,
captivity and prior Native town/encounter globals. Prior globals are not proof
of an active menu. NPC speech is prohibited in battle-mode missions.
Revision 4 chains asynchronous HTTP responses with a 250ms bridge wait, keeping
campaign/menu telemetry fresh without advancing time. Poll nonces stop superseded
responses from creating duplicate callback loops. Native entry hooks cover all 217
menus; return/map consequences clear the active menu context. Legacy triggers
remain as recovery seeds. If HTTP fails while paused, opening a menu or advancing
time is still needed to restart the loop; this is not automatic outage recovery.
State older than 15 seconds is marked disconnected. Commands expire after
30 seconds and are replayed until acknowledged. Player troop slots 99940–99999
are reserved for deduplication, result codes, mission sessions and NPC targeting.
Do not reuse these slots in other mods. Mission actions are scoped to scene and
mission session and revalidated in game code. Bridge restart or mission-clock
reset cancels queued mission actions and marks already-dispatched ones interrupted
rather than replaying them blindly. An interrupted command may have executed;
inspect state/events before issuing a replacement.

## Setup

From this project directory, `uv sync`. Start the bridge in a tmux window:

```bash
uv run python -m bridge.game_bridge \
  --token-file /tmp/shuvcode/warband-cua/bridge.token \
  --database /tmp/shuvcode/warband-cua/bridge.sqlite --create-token
```

Omit `--create-token` on subsequent starts. Keep the database across restarts.
After building the mod, restart the bridge with
`--catalog /tmp/shuvcode/warband-cua/WarbandMCP/mcp-catalog.json` for troop names.
The bridge binds only 127.0.0.1. Vanilla Warband's HTTP transport is documented
to use port 80, so the game URL defaults to `http://127.0.0.1`, while MCP connects
directly to 8765. On this Linux test host a temporary, explicitly approved
`warband-mcp-port80.service` forwards loopback port 80 to 8765. It runs as the
user with only `CAP_NET_BIND_SERVICE`, not as a root Python server. This is test
infrastructure, not an MCP dependency. Other hosts can run the bridge directly
on port 80 (`--port 80`) if permitted, and set `WARBAND_BRIDGE_URL` accordingly.
Do not change global privileged-port policy or firewall rules for this.

The approved temporary forwarder can be created with:

```bash
sudo systemd-run --unit=warband-mcp-port80 --collect \
  --property=User="$USER" --property=AmbientCapabilities=CAP_NET_BIND_SERVICE \
  --property=CapabilityBoundingSet=CAP_NET_BIND_SERVICE \
  --property=NoNewPrivileges=yes /usr/bin/systemd-socket-activate \
  --listen=127.0.0.1:80 --now /usr/lib/systemd/systemd-socket-proxyd 127.0.0.1:8765
# Stop only this temporary service when finished:
sudo systemctl stop warband-mcp-port80.service
```

The random token is embedded in the mod and
required by both the game's polling URL and MCP API requests. Don't publish
compiled strings.txt or the token file. This protects against accidental local
requests, not other local users able to read the module. Don't expose this HTTP
server externally; its game transport is plain HTTP and intentionally local.

Build a **new** Native-based module; the builder refuses an existing destination:

```bash
uv run python -m module_system.build_mcp_module \
  --native '/home/shamanic/.local/share/Steam/steamapps/common/MountBlade Warband/Modules/Native' \
  --output /tmp/shuvcode/warband-cua/WarbandMCP \
  --token-file /tmp/shuvcode/warband-cua/bridge.token
```

The test installation links that output into `Modules/WarbandMCP`. Select it in
the launcher, then enter Tutorial → free-play training ground. Leave it unpaused
to receive telemetry. Do not run the legacy `build_module.py` on this module.
Native, Pendor, and the previous ExternalAPI prototype are not overwritten.

## Mod source provenance

`module_system/build_mcp_module.py` contains readable operation lists plus an
additive bytecode writer. It verifies the Native callback is empty and copies
all Native assets before changing seven files, preserving existing IDs/scripts.
It doesn't use the old prototype's incorrect opcode definitions.

Official ModSys 1.171 mirror, pinned commit
`f718b182eb25ae21c3095e89bdba5d95158a682f`:

- [Operation definitions](https://github.com/int19h/mb_warband_module_system/blob/f718b182eb25ae21c3095e89bdba5d95158a682f/Module_system%201.171/header_operations.py)
- [URL callback protocol](https://github.com/int19h/mb_warband_module_system/blob/f718b182eb25ae21c3095e89bdba5d95158a682f/Module_system%201.171/module_scripts.py#L9240-L9261)
- [Vanilla custom-port restriction](https://forums.taleworlds.com/index.php?threads/send_message_to_url-returns-error-as-only-string.382407/)

The game parses pipe-separated HTTP replies into integer `reg` and string `s`
registers. The callback checks a magic number, protocol version, argument counts,
command ID and allowlisted opcode before executing. No arbitrary script commands
are accepted from the bridge.
Compiled string values must not contain underscores in HTTP URLs: Warband renders
them as spaces. The census completion endpoint is deliberately `/agents-end`.
New dialogue lines follow Native's initial conversation-variable setup; existing
dialogue states retain their IDs and the new state is appended. The custom line
checks both troop and agent ID, so it cannot replace another NPC's conversation.
NPC text is held in string register 126, then copied to register 60 in the matching
dialogue condition after Native's conversation setup. Do not interpolate `{s126}`
directly (unsupported token), or use `s63` (Native overwrites it with relationship
text). Builder tests protect the emitted token, but only live CUA inspection can
verify Native setup and the actual rendered line.

## Native battle orders (revision 6)

`warband_battle_order(formation, order)` executes `team_give_order` for the living
player agent's **own team** only. Requires a battle-mode mission, no dialogue,
and matching scene/session. Formation 0–8 selects a division; 9 selects everyone.
15 Native orders are allowlisted, including retreat (can lose the battle).

`warband_battle_order_result(command_id)` returns durable engine read-back per
division: movement, fire, riding, weapon use and the existing order position.
`complete` means all expected rows arrived, not that troops obeyed or won.
Hold uses the engine's existing order position; custom formation placement is
not yet implemented. Native fire/riding/weapon getters use distinct enums from
the command IDs; the response provides the mappings.

Live verified in Native Custom Battle (`quick_battle_battle`, scene 524): hold fire,
fire at will, follow and hold. Four acknowledgements, nine matching division
read-backs each. CUA capture independently shows all four Native order messages.
Original proof: `evidence/battle-orders/`. Reproduce with
`bridge/smoke_battle_mcp.py`. The other 11 orders have game implementation and
argument guards but are **not yet live-verified**. No claim of enemy control,
individual agent combat AI, player attacks or campaign-battle acceptance.
72 tests pass for the active suite; 79 opcodes checked against official ModSys.

## Individual scene controls (revision 7)

- `warband_place_formation`: bounded Native hold-point placement, own team.
- `warband_agent_wield`: select an actually equipped item, never spawn one.
- `warband_move_npc`: scripted NPC walking within scene bounds, not teleport.
- `warband_release_npc`: clear NPC scripted mode and request AI rethink.
- `warband_agent_combat`: directional attacks/blocks, explicitly requiring fresh
  engine read-back. NPC combat takes scripted control; release afterwards.

permits other teams, as a world intervention (override still unverified).
Commands are living-agent, dialogue, scene and session guarded. Fresh census

destination. An acknowledgement alone is not evidence of movement or damage.

The acceptance harness fails on player input unless `--npc-acceptance` explicitly
limits acceptance to NPC/formation controls; player failure stays in the evidence.

Late callbacks previously accessed unloaded troop slots at the main menu. An
